Components — who is who

The boxes in the diagram, one by one.

Web Browser «client»HTTP + WebSocket

Your laptop or phone. It does not speak ROS — only HTTP (REST) and WebSocket. Everything "ROS" stays inside Kevin. The browser is one side of the boundary; mir_ui and rosbridge are the translators on the other side.

mir_ui «FastAPI orchestrator»:80

The brain / receptionist. It serves the web page and the REST API on port 80, and it coordinates everyone else.

  • Receives every request, checks the login token, and validates the body (Pydantic).
  • It never touches the robots directly. It reads data over HTTP/DDS and delegates commands.
  • It holds the Docker socket — the master key that lets it run commands inside the other containers (docker exec).
mir_ur_driver «the arms container»:9090 :9091 · RTDE

The container that talks to the UR5e arms. Several things run inside it at once — click each:

UR driver — ros2_control (hardware interface + controllers)

Started on demand by the Start driver button (runs ur_start.sh → ros2 launch duo_ur duo_ur_real.launch.py). It brings up ros2_control:

  • Hardware interface (left_ur / right_ur): the only part that actually speaks RTDE to each arm, ~500 Hz.
  • Controllers (joint_trajectory_controller to move, freedrive_mode_controller to hand-guide): they translate high-level goals into RTDE commands. Each exposes an action server.
rosbridge :9090

A ROS ↔ WebSocket translator. It lets the browser (which can't speak ROS) subscribe to topics over WebSocket — we use it for the camera image (converted to base64).

joint_server :9091

The "whiteboard." A tiny HTTP server that subscribes once to /joint_states and keeps the latest value in memory (QoS depth=1). On GET /joints it returns that value as JSON instantly (~5 ms) — no ROS work per request. It decouples ROS (pushes ~500 Hz) from the browser (pulls every 250 ms).

action_bridge

A helper that exposes higher-level actions (e.g. home poses) used by skills.

joint_mover (runs per command)

Not a long-running service — it runs once per move when mir_ui launches it via docker exec. It reads the current pose from joint_server, builds a 2-point trajectory, and sends it as a ROS action to the controller.

mir_camera «container»

Runs the Orbbec camera node. It reads the camera over USB and publishes the image on a ROS topic (already JPEG-compressed). rosbridge picks it up for the browser.

mir_mir «MiR bridge»

The MiR runs ROS 1 internally; we use ROS 2. This container runs mir_raw.py (Eemil's code): it connects to the MiR's rosbridge over WebSocket, auto-discovers its topics, and re-publishes each one in our ROS 2. A liveness probe + watchdog restart it if it goes silent.

Hardware «external»
  • UR5e arms (.102 / .103) — reached by the driver over RTDE.
  • MiR200 (.13) — its own REST API (HTTP) + rosbridge (ROS 1, WebSocket).
  • Orbbec camera — over USB to Kevin.

Key flows — how data travels

Follow a piece of data end-to-end.

Reading joint positions
  • The driver speaks RTDE to the arms and publishes /joint_states at ~400–490 Hz.
  • joint_server keeps the latest value (the whiteboard); mir_ui's /api/ur/joints proxies it (100 ms cache).
  • The page polls every 250 ms — a single shared poller feeds both the numbers panel and the 3D viewer.

Why HTTP, not docker exec per read: spawning a process per read took ~200 ms; the persistent server answers in ~5–10 ms.

↳ The joint_server, in depth (the "latest JSON")

Problem: the driver publishes /joint_states ~500×/second; the browser doesn't speak ROS, and opening a fresh ROS connection per read took ~200 ms.

Solution: a tiny program inside the driver doing two things at once (two threads):

  • As a ROS node: subscribes once to /joint_states and keeps only the newest message in memory (QoS depth=1).
  • As an HTTP server on :9091: on GET /joints it returns that value as JSON instantly (~5 ms).

Analogy: a whiteboard. The robot keeps writing its position; whoever needs it just reads the board, instead of interrupting the robot each time.

The JSON is already "chewed" — split into left/right, with age_s and a stale flag:

GET http://localhost:9091/joints  →
{
  "left":  { "shoulder_pan": -0.01, "elbow": -1.57, ... },
  "right": { "shoulder_pan":  0.02, "elbow": -1.20, ... },
  "age_s": 0.012,    // 12 ms old
  "stale": false     // true if > 2 s without data
}
↳ How the driver talks RTDE, in depth
  • RTDE is UR's real-time channel over TCP (ports 30001-30004). The driver keeps it always open and, ~500×/s, reads state (positions, velocities, forces) and writes commands.
  • Inside the driver runs ros2_control in two layers: a hardware interface (the only part that actually speaks RTDE) and, on top, the controllers that turn high-level goals into commands.
  • On the robot, the URCap "External Control" program must be running to hand real-time control to the driver. If it stops, commands are rejected — that's why recovery calls resend_robot_program.
Moving a joint the key flow
  • The browser sends POST /api/ur/move with {arm, joint, delta} to mir_ui.
  • mir_ui validates (Pydantic: valid joint, |delta| ≤ 0.5 rad). Bad command → rejected here, never reaches the robot.
  • In a worker thread, mir_ui runs joint_mover.py inside the driver via docker exec.
  • joint_mover reads the current pose, builds a FollowJointTrajectory goal (2 points: now → target, over N seconds) and sends it to the controller.
  • The joint_trajectory_controller interpolates and streams commands to the arm over RTDE. On SUCCEEDED, the API returns "ok".
↳ What the controller does with the trajectory

The joint_trajectory_controller is an action server: it takes the goal (2 points — now → target, over N seconds) and interpolates, streaming many in-between points to the arm over RTDE. Not a jump — a smooth, point-by-point motion.

  • Why 2 points + a duration: the first point (current pose) avoids a jerk at start; the duration (≈3 s for 0.1 rad) sets the speed.
  • Done? the ROS action returns SUCCEEDED; then the API replies "ok".
  • If it fails (rejected / controller down / timeout — typical if the UR's external program stopped): the backend calls resend_robot_program, reactivates the controller and retries once.
How the controller is born (and why joint_mover reaches it)

We don't insert a controller — it is created when the driver launches. ur_start.sh runs ros2 launch duo_ur duo_ur_real.launch.py, which starts ros2_control: the hardware interface (RTDE) plus the spawned controllers, all as processes inside mir_ur_driver.

The twist: joint_mover reaches the controller not because they share a container, but because they share the same ROS graph (same ROS_DOMAIN_ID + host network). joint_mover opens an ActionClient by name, and DDS discovers the controller's action server. It would even work across different containers — they're together because it's simplest.

Setting the payload (a ROS service)

Here the conversion is to a ROS 2 service (request → response), not an action. mir_ui turns {arm, mass, cog} into a ros2 service call … set_payload. The arm stores it to compensate gravity and detect collisions. No movement.

Freedrive (hand-guide)

Switches the arm's controller from joint_trajectory_controller to freedrive_mode_controller, then publishes a 10 Hz "deadman" so it stays compliant (auto-disengages if publishing stops).

Requires an active payload > 1 kg on that arm first, so it holds its own weight when it goes compliant. The UI blocks enabling until a payload > 1 kg is applied.

Camera stream

Step by step:

  • The camera connects to Kevin over USB. The mir_camera container launches the Orbbec node (ros2 launch orbbec_camera gemini_330_series.launch.py).
  • That node publishes a ROS 2 topic: /camera/color/image_raw/compressed. "Compressed" means the image already arrives as JPEG (lighter for the network).
  • rosbridge (which lives inside mir_ur_driver) subscribes to that topic and exposes it over WebSocket. As it does, it converts the JPEG bytes to base64 (text) — exactly what a browser can drop straight into an image.
  • The browser uses roslib.js to subscribe over WebSocket and puts the result in <img src="data:image/jpeg;base64,…">.

Conversions: raw image → JPEG (at the camera) → base64 (at rosbridge).   Transport: USB → DDS (ROS 2) → WebSocket.

MiR telemetry (REST)
  • mir_ui does GET http://192.168.1.13/api/v2.0.0/status and maps the big JSON to a clean one (battery_percentage → battery_pct, etc.).
  • The MiR answers intermittently, so the backend caches the last value for 20 s and serves it flagged stale if the MiR is silent.
MiR ROS 1 → ROS 2 bridge

mir_mir connects to the MiR's rosbridge over WebSocket, auto-discovers its topics, and re-publishes each in ROS 2. Per-message conversions: secs/nsecs → sec/nanosec, drop Header seq, CameraInfo D/K/R/P → d/k/r/p, clamp DiagnosticStatus.level.

3D viewer

Opens no new connection — it reuses the joints poller. With the 12 angles and the kinematic chain (ur5e_chain.json, from the URDF) it draws each arm with primitives (cylinders + spheres) in Three.js and rotates each joint live, on a simulated torso.
